# Native client controls

Build the standalone Fabric test mod with `bash src/test/client/build.sh` and run its focused validation with `python3 src/test/client/test.py`. The output is `build/client-automator/InstanceAutomator.jar`. The default game version is 26.3. Set `AUTOMATOR_MINECRAFT_VERSION=26.2` to build the GLFW/Blaze3D bridge into `build/client-automator/26.2/InstanceAutomator.jar`. Stop the owned client completely before replacing that file in its profile.

The bridge accepts authenticated loopback requests at `POST /command`, with `X-Automator-Token` and a JSON `op`. Requests dispatch on the native game thread. Inspect `GET /state` for the active screen, visible widgets, cursor and pending input before the next interaction.

Run the native portal edge-case suite with `python3 src/test/client/gametest.py`. Add `--minecraft-version 26.2` to select the 26.2 adapter, dependency pins, test resources, and bridge; the default is 26.3. It uses an isolated hidden 1920×1080 GPU client with the pinned Sodium version and muted master audio, verifies visibility, focus, mouse capture, and advancing frames, rejects protocol resets and native frame failures, and removes its owned runtime when done. Logs, screenshots, and results stay under ignored `.qa/native-client/`. Select individual fixtures with names such as `PortalHorizon AngledCrossing PortalRotation`, choose `--renderer vanilla` for the vanilla renderer, or use `--suite compatibility` for the separate platform and projection checks. `--shader-pack /path/to/pack.zip` installs the pinned Iris runtime and enables that pack for any selected fixtures; `--suite shader` requires this option.

The default suite covers opposing horizon heights, all three supported rotation axes, combined frame rotations, shallow and glancing crossings, aperture rims, side entry, immediate reversal, intact floor collision, recursive entities, mirror water, shaped apertures, dimensional doors, and portal size differences. Native frame rotations use the API's quarter-turn positions. The falling-loop fixture primes one crossing with frozen entities, then checks three player crossings with the entities falling. It stops after four crossings total and does not require terminal velocity.

`ClientViewScene` checks particle suppression while the client is inactive, then exercises the foreground branch through a scoped logical-activity hook at `WormholesClient.tick`. The native window remains hidden and unfocused, with its mouse released. Acceptance requires at least eight real dust particles from the production RTP rim emitter in the native particle queue. The fixture then requires suppression when logical activity ends. It restores its scope and particle setting after each scenario.

`SeamlessSameDimension` requires a real native turn during its turning crossing. `CrossingComposition` checks a lit destination wall in composed GPU frames immediately before travel and the first eight destination frames. Its singleplayer routes cover far and near same-dimension crossings, an Overworld-to-End crossing, and each return. Every sampled frame must retain the bright destination surface. Screenshots remain in the run's ignored evidence directory. Framebuffer readback adds cost, so use a separate run of `SeamlessSameDimension` for timing comparisons. Add `--jvm-arg=-Dwormholes.clientgametest.captureCrossingFrames=true` to other travel fixtures to retain four frames after each level change or large camera jump, including setup teleports.

`AdjacentSourcePortals` opens two adjacent coplanar Overworld frames linked to separate Nether rooms. Stationary preparation waits for both views to appear together before the first crossing; preparation frames remain in the evidence. The fixture walks out and back through each pair for four accepted crossings, without a warmup crossing. It captures every active frame. An independent server-authored ray model checks direct wall surfaces and recursively visible aperture interiors, including first visibility after camera turns. Each crossing requires at least 40 arrival frames with direct wall samples. A return aperture can fill the viewport close to its plane, leaving no direct wall samples in that frame. Reduced copies of both real source apertures and a gray aperture must fail the same image oracle in offline negative controls. Wrong-world streamed roots must also remain unavailable. Evidence stays in `screenshots/adjacent-source-portals/` under the ignored run directory. Add `--jvm-arg=-Dwormholes.clientgametest.adjacentPortals.capture=false` for a fresh uncaptured timing run with ordinary camera effects. Its provenance records native crossing cost, arrival render cost, and frame intervals for the first four crossings. Captured intervals include readback overhead and do not prove performance. Add `--jvm-arg=-Dwormholes.clientgametest.adjacentPortals.secondFirst=true` to cross the second opening first. The image oracle samples an eight-pixel grid with explicit block and aperture margins. Each sample must match the ray model one pixel in all four cardinal directions, excluding uncertain rasterized silhouettes. Capture runs use a 20 FPS cap and timing runs use 120 FPS. It does not certify unsampled pixels or recursion beyond three.

For uncaptured timing correlation, add `--jvm-arg=-Dwormholes.clientgametest.profileFrames=true` and a `-XX:StartFlightRecording` JVM argument with an ignored output path. The `wormholes.ClientFrame` JFR events span consecutive rendered frame ends and record the arrival dimension, resident level identity, camera position, and frame index. These intervals include client-test scheduler waits and frame pacing, so they do not measure rendering alone.

The paired `wormholes.ClientRender` events span `GameRenderer.render` entry to return, before capture at the frame-end tap, and record the frame index, arrival dimension, and resident level identity. Correlate both event types with JVM samples and GC; profiler attachment and recording affect timing. The optional `wormholes.ClientRenderPhase` events record inclusive method spans, parent span ids, frame and world identities, and render-thread CPU time when the JVM supports it. Use timestamp containment or span relationships when comparing phases; do not add nested inclusive durations.

`NetherCrossingComposition` uses native flint-and-steel ignition and managed conversion of an ordinary three-wide Nether frame. It records centered held-W traversal and a 75-degree near-plane crossing with immediate reversal, with asymmetric colored markers around the real endpoints and the HUD hidden during capture. The spatial check uses a fixed 70-degree field of view without view bobbing or dynamic FOV effects; ordinary traversal timing retains normal camera effects. Every rendered framebuffer and its camera, player, projection, arm, and view provenance remain under `screenshots/nether-composition-*/` in the run evidence. A conservative spatial exclusion check rejects marker pixels outside projected scene footprints and must reject a duplicated real-frame crop in its separate test-only oracle. This does not certify the complete composed image or exclude duplicates inside allowed footprints; review the retained sequence on matched 26.2 and 26.3 runs. Capture readback and PNG writing affect frame times, so keep uncaptured traversal timing separate. `--renderer vanilla` selects Fabric plus Wormholes using Minecraft's vanilla renderer.

`NetherCrossingEffects` exercises the same native Nether routes with normal view bobbing and dynamic FOV effects enabled. Each route starts with centered walking. The oblique route turns to 75 degrees near the opening and requires that yaw in the accepted native crossing. It records the final effect-adjusted projection and checks known wall colors against geometric ray intersections in every captured crossing frame. Capture uses a 20 FPS cap to keep lossless readback within its bounded queue. Use a separate uncaptured fixture for timing.

Construction-recorded obsidian cuboids account for foreground occlusion in both worlds. A separate bounded image-readiness phase checks each visible wall path and saves its evidence before walking starts. Each first destination frame needs at least 64 wall samples, and a real framebuffer crop reduced inside the opening must fail the same oracle.

A bounded worker processes lossless PNG writes without DEFLATE compression, pixel inspection, and crop controls in frame order. It accepts at most 32 outstanding frames, including GPU callbacks, and fails on overflow instead of dropping frames. Provenance records queue counts and drain state. GPU readback and geometric probe construction still affect rendering, so these capture times are separate from uncaptured performance evidence.

This spatial scene selects `OFF` for ambient particles and waits for main-world particle queues and opening animations to finish. That wait does not certify expiry of particles stored in other resident worlds. Wrong colors and any remaining particle-contaminated samples remain failures. This checks selected scene samples rather than every pixel, and its warmed capture run does not measure cold crossing performance.

The fixture records the original player, source and destination levels, native crossing arguments, and return value. Accepted travel, source changes, resets, and failure cleanup stop the input.

`CardinalLighting` reads the actual OpenGL lighting buffers for Overworld and Nether directions. It requires separate immutable buffers, stable reuse across 64 world switches, immediate restoration of selected world lighting, independent inventory and external shader bindings, and independent lighting instances. It counts native world-lighting writes and requires zero writes during these switches. Closing an instance must release its world buffers and native inventory buffer. Run this fixture on both game versions with `--renderer vanilla`; it checks GPU state rather than the complete rendered image.

Run `VanillaPipelinePreparation` on both game versions with `--renderer vanilla`. At the title screen, it requires all 16 fixed portal products to be linked before world or portal creation. Its JFR event duration does not measure that call. Preparation wall time includes its native calls, so do not add these durations together.

Every Fabric rig run enables `wormholes.test.fabricPhasedShutdown`, independently of the renderer, shader pack, and DH. When Fabric’s client GameTest scheduler is active, off-thread `halt(false)` queues native integrated-server halt on the owning server thread. This lets the render thread advance the test phases while native player removal, saving, and stopping finish. Fabric’s singleplayer context still waits for the server loop to exit and the client world to close; synchronous halt and production runtimes retain native behavior. The mixin requires the Fabric GameTest marker and scheduler class and is packaged only in the test runtime.

The Fabric-only tap is active only during each tested crossing; arrival direction, aperture, camera continuity, packet and roll checks remain required in singleplayer and dedicated-server runs.

- `keys` supports `playerList` alongside movement and inventory keys, with a bounded tick lease.
- `pause-screen` opens the real pause menu of a connected player through native `pauseGame(false)`.
- `chat-screen` opens the real chat screen with optional `text`; `clear-chat` clears its displayed history while preserving command recall.
- `cursor` moves the visible virtual cursor on native screens. `gui` supports widget listing, native click, key, text and close operations. GUI clicks translate protocol left/right buttons to native SDL or GLFW buttons for the selected game version; container slot clicks retain protocol buttons.
- `anvil-name` types into the focused native anvil text field. `sign-text` selects line 0–3 before typing. Both accept `text`, `replace` and `ticksPerChar`; input is bounded to 512 printable characters and 1–20 ticks per character. Wait until `textPending` is false before submitting or changing screens.
- `server-list` opens the actual multiplayer screen from a disconnected client with an explicit `127.0.0.1:<port>` address and optional display name.

These controls operate real client UI. They do not insert synthetic chat messages, alter renderer output or substitute screenshots for recorded playback.
